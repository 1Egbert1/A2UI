# 长期方向：A2UI 能立住什么，以及 Chrome 那套协议打开了什么空间

> **先说明我理解的「Chrome 当前那套协议」**：指 Chrome 现在围绕 agent 的三件东西——
> **Chrome DevTools for agents**（agent 驱动浏览器）、**WebMCP**（站点给 agent 暴露工具）、
> **Chrome 内置 AI**（Gemini Nano 端侧模型）。如果你指的是 CDP 本身或 Chrome 扩展 API，说一声我换角度。

---

## 一、现状盘点（2026-10）

| 面 | 协议 / 产品 | 现状 | 它解决什么 |
| --- | --- | --- | --- |
| **驱动 UI** | Chrome DevTools for agents（`chrome-devtools-mcp`） | **1.0 稳定**，MCP + CLI + skills，26 个工具 | agent 能像真人一样操作与检查浏览器：点、填、截图、看网络、录性能、跑 Lighthouse |
| **暴露工具** | WebMCP | **Origin Trial** | 站点不再靠 agent 猜 DOM，而是显式声明工具给 agent 调 |
| **运行模型** | Chrome 内置 AI（Gemini Nano） | Summarizer / Translator / LanguageDetector **稳定**；Prompt API 扩展侧稳定、网页侧 2026 年内逐步稳定；Writer / Rewriter / Proofreader 仍在开发预览 | 浏览器本身就是模型运行时：免费、离线、数据不出设备 |
| **发出 UI** | A2UI（Google + AG-UI 生态） | v0.9.1 current，v1.0 RC；配套工具 A2UI Composer | agent 用声明式 JSON 描述界面，宿主用自己的组件渲染 |

**关键观察**：Chrome 把「驱动 UI」「暴露工具」「运行模型」三个面都做成了 agent 可用的协议。
**唯独「发出 UI」这一面，Google 给的是规范 + 编辑器，没有给出可验收的运行时**——这正好是你已经做了一半的事。

端侧模型还有一条对本项目直接相关的特性：Prompt API 支持 `responseConstraint`（JSON Schema 约束输出）。
**模型输出协议 JSON 这件事，正在从「靠提示词」变成「靠 schema」**，而我们的 `recoverJson` 是「schema 之下的最后一道修补」。

---

## 二、由 Chrome 那套带来的特殊场景

这些都是 Chrome 已经实现、但**没有人用它来验收生成 UI** 的能力：

| Chrome 已有能力 | 放到生成 UI 场景里 |
| --- | --- |
| Lighthouse 审计（a11y / SEO / best practices / agentic browsing） | **生成界面的质量门禁**：不合格就不给渲染 |
| 无障碍调试 skill | 生成界面的语义正确性（现在生成的卡片大多没有 a11y 属性） |
| 内存泄漏调试（heap snapshot、detached DOM） | 多轮增量渲染是否会越改越漏 |
| 设备 / 网络 / CPU 模拟 | 生成界面在弱网、低端机、小屏的表现 |
| 截图 + DOM 检查 + JS 执行 | **与参考图逐项比对**（正是你那个百度复刻案例要解决的） |
| WebMCP 调试 | 生成界面自带的工具能不能被正确调用 |
| 第三方 devtools 暴露内部状态 | 生成界面的数据绑定状态能被外部读取与诊断 |
| 会话移交（auto-connect） | 登录态下调试生成界面 |

## 三、这个项目已经立住的三个点

1. **生成质量工程** —— 分块 prompt 规约 + `recoverJson` 结构化容错 + 26 条可机检评测。
   这套与协议版本解耦，换到 v0.9/v1.0 依然成立。这是**唯一别人抄不走的部分**（抄代码容易，抄判断难）。
2. **可私有化 + 国内模型链路** —— 自己的 Key、自己的服务器、离线 mock 可跑通。Composer 是 SaaS。
3. **Vue 渲染器 + 中文业务场景** —— 官方与 Composer 都是 React；10 个业务用例（订单/点餐/酒店/工单…）是目录的雏形。

---

## 四、三个候选的长期项目

### A. 可验证的生成 UI（self-verifying UI）★ 推荐

**做什么**：让「生成 → 渲染 → **验收** → 修正」成为一个闭环。
界面渲染后由浏览器回读（截图 / AXTree / DOM 几何），与参考图或断言比对，不合格就带着差异信息回到 prompt 修正——复用已有的 `@id` 组件点选能力做定点反馈。

**为什么现在做**：Chrome DevTools for agents 1.0 已稳定，MCP 一连就能用；而你的 26 条评测**只验结构合法性，不验「长得对不对」**。图片复刻那个案例，现在只能靠人眼判断还原度。

**独特性**：Composer 有 Gallery 没有评测；官方 SDK 有 schema healing 没有验收。
**「生成 UI 的 CI」这个位置目前是空的。**

**第一年里程碑**：
1. 结构断言（已有）→ 2. 视觉断言（关键元素的盒模型、颜色、文本）→ 3. a11y / 弱网 / 小屏门禁 →
4. 失败自动回写 prompt（闭环）→ 5. 每个行业目录配 10 个验收用例 → 6. 开源「A2UI 验收套件」

**风险**：视觉 diff 不稳定（字体、动画、抗锯齿）；必须先定义「验收什么」，否则会陷入像素对比的泥潭。**建议从「关键元素几何 + 文本」开始，不做全屏像素 diff。**

### B. 双向协议：A2UI + WebMCP 闭环

**做什么**：生成的界面不只是静态描述，还**声明工具**；用户点按钮触发工具，工具结果回填数据模型，界面再更新。
A2UI 管「agent → UI」，WebMCP 管「UI → agent」，两者闭合成一条完整的交互链。

**为什么现在看**：WebMCP 还在 origin trial，**现在入场有先发优势**，但也有 API 变更风险。
**适用场景**：企业内部工具、审批流、数据录入——这类界面的核心价值不在「好看」，在「能办事」。

**风险**：协议未稳定；需要浏览器端配合（Chrome 之外不支持）。

### C. 端侧模型生成 UI（离线 / 隐私）

**做什么**：用 Chrome 内置 Gemini Nano + `responseConstraint`（JSON Schema）本地产出 A2UI JSON，完全离线渲染。
配合已有的 `recoverJson` 兜住小模型的输出缺陷。

**适用场景**：内网、敏感数据（医疗 / 金融 / 政务），**数据不出设备**是刚需而不是加分项。
**风险**：端侧模型的协议遵循能力弱（这是硬伤），硬件门槛约六成用户；更适合做「降级路径」而非主路径。

---

## 五、推荐 A，理由三条

1. **复用已有资产**：26 条评测、图片复刻案例、容错机制都是现成的，不需要从零开始。
2. **顺势而非对抗**：它建立在 Chrome 已经稳定的工具上，不赌任何未定协议（B 赌 WebMCP，C 赌 Nano 的能力上限）。
3. **位置是空的**：生成侧已经很卷（Composer、AG-UI、CopilotKit），**验收侧没人做**。
   而「能不能进生产」最终取决于验收，不取决于生成得多快。

## 六、如果选 A：六个月路线图

| 月 | 目标 | 产出 |
| --- | --- | --- |
| 1 | 把 26 条结构断言接进 CI，并定义「验收什么」 | 断言规范文档 + CI 门禁 |
| 2 | 视觉断言脚手架（Playwright / CDP 回读 DOM 几何） | 关键元素盒模型 + 文本断言 |
| 3 | Lighthouse a11y 门禁 + 弱网 / 小屏模拟 | 可访问性与响应式验收 |
| 4 | 失败自动回写 prompt（用 `@id` 做定点反馈） | 闭环：生成 → 验收 → 修正 |
| 5 | 行业 catalog（电商 / 工单 / 酒店）+ 每行业 10 个验收用例 | 30 个带验收的业务用例 |
| 6 | 对外开源「A2UI 验收套件」 | 项目从「实现」变成「标准工具」 |

## 七、边界（别做的三件事）

1. **不要先去追 v1.0**：互通能力（方言转换器）优先于版本号。
2. **不要重写多端渲染器**：React / 小程序是 P2，先让 Vue 这一份「可验收」。
3. **不要做编辑器**：Composer 已经占住「怎么写对」；你要占的是「怎么验证对」。

## 八、可以做成什么产品形态

同一个代码库，往四个方向长出来的东西完全不同。先摆清楚卖给谁、交付什么、钱从哪来。

| 形态 | 客户 | 交付物 | 收费点 | 前置依赖 | 难度 |
| --- | --- | --- | --- | --- | --- |
| **① 私有化 AI UI 运行时** | 中大型企业的内网工具团队 | 三容器栈（gateway/web/server）+ 行业 catalog + 模型适配 | 年度授权 + 实施 | v0.9 兼容、持久化、多租户 | 中 |
| **② 生成 UI 的验收服务** | 前端平台团队 / ISV | CLI + CI 插件 + 验收报告 | 按项目 / 按次 | 视觉断言引擎、判定标准 | 中偏难 |
| **③ A2UI Studio（生成工作台）** | 中小团队、产品与设计 | 浏览器工作台：对话改界面、导出协议/代码 | 订阅 | 与 Composer 正面竞争 | 难（红海） |
| **④ 行业 Catalog 包** | 集成商、ISV | 每行业一套：catalog + 提示词 + 验收用例 + 示例数据 | 按包售卖 / 分成 | 依附 ①或② 做载体 | 容易起量，难做深 |

### 8.1 ①私有化运行时：最直接能收钱的形态

客户买的是「**在我内网里，用我自己的模型，生成我的界面**」。这件事 Composer 给不了——它是 SaaS、模型通道也在它手里。

需要补的三件事，都不是技术难点，是产品必需：**会话持久化**（现在是进程内 Map，重启即丢、多实例不共享）、**多租户与配额**、**审计留痕**（谁在什么时候生成了什么）。

### 8.2 ②验收服务：差异化最强，但要先立判定标准

对标物是视觉回归（Chromatic / Percy 一类），但对象换成「AI 生成的界面」。核心资产是 26 条用例 + 抽取容错 + 未来的视觉断言——**这些是别人最不愿意从头造的**。

风险在判定标准：全屏像素 diff 一定会失败（字体、动画、抗锯齿）。必须先立「验收什么」：关键元素几何 + 文本内容 + a11y 角色，放弃像素级。

### 8.3 ③Studio：不建议单独做

Composer 已经占住「怎么写对」，v0.2dev / CopilotKit 也在同一个位置。再做一个生成工作台，等于用最弱的资源打最挤的战场。**可以做，但要作为 ① 的附属界面，而不是独立产品。**

### 8.4 ④行业包：最好的增值，不是主线

订单、点餐、酒店、工单、课表这些场景已经在 26 条评测里跑通了。把它们固化成「catalog + 提示词 + 验收用例 + 假数据」，是**别人最难复制**的东西——协议谁都能实现，业务目录不行。但它需要一个载体（①或②），单独卖包没有渠道。

**推荐组合：① 收钱、② 建壁垒、④ 做增值。③ 只做附属。**

## 九、演进路线：按层拆，按半年排

### 9.1 协议与互通（0–6 个月）

| 优先级 | 做什么 | 为什么 |
| --- | --- | --- |
| P0 | 方言转换器（v0.8 ↔ 新方言） | 一周成本换互通能力，先能读 Composer 的产物 |
| P1 | 迁 v0.9.1：`createSurface` / `surfaceProperties` / 客户端函数 | 版本债越拖越贵，有转换层后可分步 |
| P2 | catalog 协商（声明本端支持什么） | 换设计系统不动 prompt 的前提 |
| P2 | 多 surface（弹窗 / 侧栏独立 surface） | 复杂产品形态的最低要求 |

### 9.2 运行时与渲染（6–12 个月）

- **设计令牌化**：42 个样式属性收敛成 token（color / spacing / radius / typography），让宿主设计系统接管，而不是让模型自由填色。这是「生成结果像不像你的产品」的分水岭。
- **多端**：优先 **Web Component**（一份实现，React / Vue / 原生都能挂），而不是再写一套 React 渲染器。
- **大列表**：现在每次刷新是全量重算，长列表（T26 那种）需要虚拟化 + 增量补丁。
- **动作闭环**：`userAction` → 服务端工具 → 结果回填数据模型，形成「点击 → 办事 → 界面更新」的完整回路。

### 9.3 生成与质量（持续）

- **结构化输出优先**：能用 `responseConstraint` / JSON Schema 约束的就别靠提示词，`recoverJson` 退为兜底而不是主路径。
- **行业 RAG**：把行业模板作为检索源，生成前先取 2~3 个同类范例，比在 prompt 里堆示例更省上下文。
- **评测接 CI**：26 条断言现成，一天的事，先做。
- **可观测性**：首字延迟、抽取失败率、组件数、token 消耗，做成一个面板——现在这些只存在于日志。

### 9.4 产品化硬门槛（现在就缺的）

| 缺什么 | 现状 | 为什么是门槛 |
| --- | --- | --- |
| 会话持久化 | 进程内 `Map`，重启即丢 | 多实例部署必然丢；无法回溯 |
| 多租户 / 配额 | 无 | 卖给第二个客户就撞墙 |
| 审计与留痕 | 无 | 企业采购的合规底线 |
| 安全边界 | 动作白名单有了（本地动作只允许 `updateDataModel` 固定值） | 但 prompt 注入面还在：页面内容、图标名、用户上传图都可能带指令 |
| 限流 | 无 | 一个用户能把模型额度打光 |

## 十、不要做什么

1. **不做通用低代码**：可视化拖拽 + AI 生成是红海，且与「协议驱动」的定位冲突。
2. **不追协议最新版当作卖点**：客户买的是「能跑、能验收」，不是版本号。
3. **不为了多端而多端**：Web Component 一条路，够用就不写第二套。
4. **不做像素级视觉判定**：会成为维护地狱，永远修不完。

---

## 十一、一句话结论

> **这个项目最像的产品是「AI 界面的运行时 + 验收器」，不是「AI 界面生成器」。**
> 生成侧已经很挤，验收侧还空着；而能不能进生产，取决于验收，不取决于生成得多快。
